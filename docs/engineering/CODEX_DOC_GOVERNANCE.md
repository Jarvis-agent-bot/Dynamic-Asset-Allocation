# Codex 核心文档守则

## 1. 目标

建立一套可执行、可审计、可持续演进的文档治理机制，确保 Codex 与人工协作在同一事实基线上推进开发。

## 2. 文档分层规则

- `docs/architecture/*`：架构与关键决策（ADR、系统边界、模块关系）。
- `docs/engineering/*`：工程流程与协作规范（工作流、验收、发布、回归）。
- `README.md`：新开发者入口与日常执行指引，不承载细节设计。

## 3. 命名规范

- 架构决策：`<TOPIC>_DECISIONS_<YYYY-MM-DD>.md`
- 规范文档：`<TOPIC>_<PURPOSE>.md`
- 路线清单：`<TOPIC>_CHECKLIST.md`
- 文件名使用大写蛇形或语义清晰英文，不使用空格。

## 4. 文档状态流转

- `Draft`：草案，允许大范围调整。
- `Accepted`：已评审通过，可指导实现。
- `Deprecated`：已废弃，必须给出替代文档链接。

每篇关键文档开头必须标记状态、日期、适用范围。

## 5. 变更提交流程（强制）

1. 需求变更或架构变更先更新文档。
2. 文档评审通过后再实施代码变更。
3. 代码 PR 必须引用对应文档路径。
4. 合并前确认文档与实现一致。

## 6. 评审清单

- 是否说明目标、边界、非目标。
- 是否定义输入/输出契约（API、类型、配置）。
- 是否覆盖异常路径与降级策略。
- 是否包含测试与验收标准。
- 是否给出迁移与回滚策略。

## 7. 引用与可追溯规范

- 引用代码时使用明确路径：`path/to/file.ts:line`。
- 引用外部信息时注明来源与日期。
- 每篇文档末尾记录“最后更新日期”和“更新人/更新方式（人工或 Codex）”。

## 8. 版本与变更记录规范

关键文档必须维护“变更记录”小节，至少包含：

- 日期
- 变更摘要
- 影响模块
- 关联 PR/任务（若有）

## 9. 与 Codex 协作约束

- Codex 在实现前必须读取相关 `architecture + engineering` 文档。
- 遇到文档与代码冲突，优先按 `Accepted` 文档判断，并在 PR 中修正冲突。
- 未覆盖的新决策必须补文档，不允许“口头约定即编码”。

## 10. 最低维护要求

- README、架构基线、工作流文档必须同步维护。
- 每个 Phase 完成后至少更新一次执行清单。
- 文档链接失效必须在当次 PR 修复。
